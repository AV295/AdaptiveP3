================================================================================
ADAPTIVE P3 (AP3) — COMPREHENSIVE PROJECT OVERVIEW
================================================================================

Your project is a **FastAPI-based Privacy-Preserving SQL Proxy** that sits 
between clients and PostgreSQL, enforcing security and privacy on every query.

================================================================================
WHAT IS THIS PROJECT?
================================================================================

**AdaptiveP3** is a middleware/proxy system that:
- ✅ Intercepts SQL queries from users
- ✅ Analyzes them for security threats (SQL injection)
- ✅ Checks user permissions and privacy budgets
- ✅ Detects suspicious query patterns (inference attacks)
- ✅ Applies differential privacy noise to results
- ✅ Tracks and audits all queries

**Think of it as a "privacy-smart firewall" for database queries.**

================================================================================
WHAT IS IT PROTECTING AGAINST?
================================================================================

1. **SQL Injection Attacks** — Malicious SQL patterns (e.g., `' OR '1'='1`, DROP TABLE)
2. **Inference Attacks** — Users making many overlapping queries to guess private info
3. **Unauthorized Access** — Role-based budget controls (admin gets more access than guest)
4. **Privacy Leakage** — Differential privacy adds noise to aggregate results to prevent 
   reverse-engineering individual data

HOW CODES ARE LINKED (DATA FLOW)
================================================================================

REQUEST FLOW FOR /query ENDPOINT:
────────────────────────────────

1. Client sends HTTP POST to /query with:
   {
     "username": "alice",
     "sql": "SELECT AVG(salary) FROM employees WHERE department='Engineering'"
   }

2. main.py receives request
   ↓
3. Looks up user "alice" in _users dict
   ↓
4. Calls middleware.proxy.process_query(user, sql)
   ↓
5. STEP 1: Analyze Query
   └─ core.query_analyzer.analyze_query(sql)
      • sqlparse library parses SQL
      • Extracts: tables=['employees'], aggregates=['avg'], sensitivity=2.5
      • Checks for injection patterns (looks for "' OR '1'='1", etc.)
      • Result: QueryAnalysis object
   ↓
6. STEP 2: Check for Injection
   └─ If analysis.is_dangerous == True
      → Return 403 error
   ↓
7. STEP 3: Role Check
   └─ If query is UPDATE/DELETE and user is not admin
      → Return 403 error
   ↓
8. STEP 4: Inference Risk Assessment
   └─ core.inference_tracker.assess_inference_risk()
      • Calls db.history_store.get_overlapping_queries()
      • Retrieves all queries by "alice" in past 1 hour that touched 'employees' table
      • Counts overlaps
      • If count >= 5 (threshold) → block
   ↓
9. STEP 5: Check Privacy Budget
   └─ core.abac.has_budget(user, query_cost)
      • query_cost = sensitivity (2.5 for this AVG query with WHERE)
      • user.epsilon_remaining = remaining budget for "alice"
      • If epsilon_remaining < 2.5 → deny (return 403)
   ↓
10. STEP 6: Execute Query
    └─ db.postgres.execute_query(sql)
       • Creates connection to PostgreSQL
       • Runs SQL: SELECT AVG(salary) FROM employees WHERE department='Engineering'
       • Returns rows as list of dicts: [{'avg': 72500.50}]
    ↓
11. STEP 7: Apply Differential Privacy Noise
    └─ If analysis.is_aggregate == True:
       core.differential_privacy.add_noise_to_resultset(rows, epsilon, sensitivity)
       • Splits epsilon budget across rows
       • For each numeric field, calls add_laplace_noise()
       • Adds random noise from Laplace distribution: Lap(sensitivity/epsilon)
       • Result: [{'avg': 72501.23}]  (noised!)
    ↓
12. STEP 8: Deduct Budget & Log Query
    └─ core.abac.deduct_budget(user, query_cost)
       • Reduces user.epsilon_remaining by 2.5
       • "alice" now has 5 - 2.5 = 2.5 left
    └─ db.history_store.record_query()
       • Stores in SQLite: (username, tables, columns, has_where, raw_sql, timestamp)
    ↓
13. Return Response:
    {
      "status": "success",
      "user": {"username": "alice", "role": "researcher", "epsilon_remaining": 2.5},
      "results": [{"avg": 72501.23}],
      "privacy_note": "Laplace noise applied to aggregate results",
      "query_analysis": {...}
    }

EXAMPLE: COMPLETE WORKFLOW
================================================================================

SCENARIO: User "alice" (researcher) runs `SELECT COUNT(*) FROM employees`

Timeline:
─────────────────────────────────────────────────────────────

T=0s  Alice registers (via POST /register)
      → Creates User(username="alice", role="researcher", epsilon_remaining=5.0)
      → _users["alice"] = User(...)

T=5s  Alice makes 1st query: SELECT COUNT(*) FROM employees
      ✓ Passes all checks (no injection, budget enough, no inference risk)
      ✓ Executed on PostgreSQL → Result: [{'count': 150}]
      ✓ Sensitivity = 1.0 (COUNT without WHERE)
      ✓ Noise applied → [{'count': 151.2}] (DP-ified)
      ✓ Budget deducted: 5.0 - 1.0 = 4.0
      ✓ Query stored in SQLite history
      ✓ Returns result to Alice

T=6s  Alice makes 2nd query: SELECT COUNT(*) FROM employees WHERE dept='Sales'
      ✓ Similar logic
      ✓ Sensitivity = 1.5 (COUNT with WHERE)
      ✓ Budget: 4.0 - 1.5 = 2.5
      ✓ Added to history

T=7s  Alice makes 3rd query: SELECT COUNT(*) FROM employees WHERE dept='Engineering'
      ✓ Sensitivity = 1.5
      ✓ Budget: 2.5 - 1.5 = 1.0
      ✓ Added to history

T=8s  Alice makes 4th & 5th queries (similar pattern)
      ✓ Budget decreases each time

T=10s Alice attempts 6th query with overlapping table
      ✗ BLOCKED: "Inference attack risk: 5 overlapping queries on table(s) ['employees'] 
                   in the last 60 min (4 with WHERE filters). Threshold is 5."
      → Returns 429 (Too Many Requests)

T=65m (1 hour later)
      History window expires
      Alice can query again

================================================================================
SECURITY MECHANISMS EXPLAINED
================================================================================

MECHANISM               PURPOSE                    HOW IT WORKS
────────────────────────────────────────────────────────────────────────────
SQL Injection Guard     Prevent malicious SQL     Regex pattern matching + multi-statement 
                                                   detection via sqlparse

Role-Based Budgets      Limit cumulative access   Each role gets an epsilon (ε) budget; 
                                                   queries deduct from it

Inference Tracking      Prevent data              Counts overlapping queries in time window; 
                        triangulation              blocks after threshold

Differential Privacy    Prevent exact data        Adds Laplace noise: Lap(Δf/ε); 
                        leakage                    higher ε = less noise

================================================================================
KEY INSIGHTS
================================================================================

1. **Modular Design** — Each security layer is separate (query analyzer, 
   budget checker, noise engine)

2. **Adaptive** — Adjusts privacy level based on user role and query pattern

3. **Audit Trail** — SQLite keeps history for forensics

4. **Non-Destructive** — Uses Pydantic's `.model_copy()` to create new user objects

5. **Differential Privacy** — Mathematically rigorous (uses IBM's `diffprivlib` library)

6. **Budget Semantics** — ε represents "privacy cost"; lower ε = stronger 
   privacy guarantee

SUMMARY

This is a production-grade prototype that combines 4 privacy technologies 
into one coherent system!

The AdaptiveP3 project is a sophisticated privacy-preserving middleware that:
- Sits between clients and PostgreSQL
- Runs 8 sequential security checks on every query
- Enforces role-based privacy budgets (epsilon)
- Detects and blocks inference attacks
- Applies differential privacy to aggregate results
- Maintains an audit log of all queries

All components are modular, testable, and extensible for production use.
